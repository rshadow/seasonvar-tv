# ADR-0059: Автослияние только PR владельца после всех проверок

Дата: 2026-11-04

Статус: Принято

Дополняет [ADR-0058](0058-github-security-checks.md). Выпуск релизов остаётся по [ADR-0053](0053-explicit-release-tag-command.md).

## Контекст

Пользователь попросил автоматически сливать именно его PR после всех проверок. Аккаунт rshadow имеет GitHub user ID 737152. PR Dependabot и других авторов должны оставаться на ручном слиянии. Через текущее подключение GitHub доступ на изменение PR ограничен; автоматизация использует штатный GitHub Actions token внутри репозитория.

## Решение

- Workflow `Auto-merge owner PRs` реагирует на события PR, завершение текущих CI-workflow и ручной запуск. Он получает только код доверенной main, не делает checkout ветки PR и не исполняет её код.
- Перед слиянием заново читать PR. Допускаются только открытые PR пользователя с ID 737152 в main, готовые к проверке; Draft исключён. Проверять ID, а не имя создателя события или ветки. Авторство bot/чужого PR не меняется от того, кто запустил проверку.
- Автослияние активно только при серверной защите main: обязательный PR, запрет удаления/force push, строгие статусы GitHub Actions из main.json и CodeQL с порогами errors/high-or-higher. Без этих правил завершаться без слияния.
- На актуальном head SHA должны успешно завершиться все семь обязательных проверок. Отсутствующий, ожидающий, отменённый или упавший результат блокирует слияние. Дополнительные проверки тоже должны завершиться без ошибок. Статус Dependency snapshot проверяется отдельно; принимается только github-actions[bot].
- Для REST merge передавать проверенный head SHA: новая версия PR, конфликт или серверное требование не должны быть обойдены. Сохранять историю обычным merge commit. По одному слиянию за проход: остальные PR требуют актуальной базы и проверок после её изменения.
- Слияние через GITHUB_TOKEN само не запускает push-workflow. После успешного merge явно отправлять workflow_dispatch для Android build, CodeQL и Dependency graph на main. Это сохраняет подписанный артефакт main и снимок зависимостей для следующих PR. Релизный тег не создаётся, публикация GitHub Release не запускается.
- Реализация — scripts/owner-automerge.py, штатная команда — make owner-automerge. Команда выполняется только в GitHub Actions; токен не сохраняется в проект и не выводится. Автономные тесты входят в make site-test и make check.
- Workflow имеет contents/pull-requests/actions write для слияния и запуска CI, checks/statuses read для проверки результатов. Checkout всегда ref: main с persist-credentials: false; source-код PR и его shell-параметры не используются.
- Репозиторный переключатель Allow auto-merge не требуется этому workflow: он выполняет защищённое REST-слияние после проверки условий. Ручное включение native auto-merge остаётся отдельной возможностью GitHub, но не используется для автоматического выбора PR владельца.
- Для изменений плеера обязательная визуальная проверка видео по правилам проекта проводится до перевода PR из Draft. Автоматические проверки не доказывают видимость изображения. Конфликты и отставшую базу автоматизация не исправляет самостоятельно.

## Альтернативы

- Native auto-merge требует отдельного включения на PR и сам не выбирает только PR владельца. Вариант с отдельным PR-токеном добавил бы новый секрет; дополнительные события main после слияния всё равно требуют учёта.
- Автослияние всех зелёных PR не соответствует выбору пользователя: Dependabot и сторонние авторы исключены.
- Слияние без server rules могло бы обойти незавершённые проверки. Отсутствие защиты считается запретом автомержа.
- Squash/rebase изменяют форму истории; выбран merge commit, сохраняющий коммиты PR.

## Последствия и проверка

Свои готовые PR после импортирования правил могут сливаться без дополнительной кнопки. Draft, конфликты и неактуальная база требуют действий автора. При добавлении новых CI-workflow обновлять список workflow_run; при необходимости повторную проверку можно запустить вручную из Actions.

Локально прошли 34 автономных Python-теста, включая 12 проверок авторизации, статусов, гонок и запуска main CI, и actionlint. Фактическую активацию проверять после импорта серверных правил; наличие файла не означает, что автомерж уже включён.
