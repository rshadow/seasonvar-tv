# ADR-0139: HTTP CONNECT в настройках сети

Дата: 2026-11-11

Статус: Принято

## Контекст

Смена DNS и DPI-обход помогают не во всех сетях. Пользователь выбрал подключение через собственный прокси с необязательной авторизацией; общий сервер проекта и настройки роутера в задачу не входят.

## Решение

Добавить в группу «Сеть» пункт «Прокси» с отдельным диалогом: тип, адрес сервера, порт, логин, пароль, «Сохранить» и «Отмена». Начальный тип — «Выключен»; первый поддержанный протокол — HTTP CONNECT. Изменения применяются только после сохранения, отмена сохраняет прежнюю конфигурацию. Поля сохраняют места при переключении типа, пароль скрыт, кнопки действий используют общий ThemeButton.

HTTP-прокси обслуживает запросы Seasonvar, постеры, плейлисты и видео через общий NetworkClients. Имя целевого HTTPS-сервера передаётся в CONNECT и разрешается прокси; выбранный DNS приложения нужен для имени самого прокси. Числовой адрес прокси не требует DNS. Запросы DoH и обновления с GitHub сохраняют собственные соединения.

Для авторизации поддержать Basic по ответу 407. Учетные данные относятся только к выбранному прокси, повторная неудача прекращает попытку; Proxy-Authorization не попадает внутрь HTTPS-запроса к сайту. Системная проверка TLS, имени сервера и pins остаётся обязательной; DPI-обход работает внутри туннеля.

Всю конфигурацию прокси хранить зашифрованной AES-GCM с отдельным ключом Android Keystore. Общий шифровальщик сохраняет формат и alias существующей сессии аккаунта. Конфигурация не выводит адрес или учетные данные через toString. При повреждении сохранённых данных показывать необходимость проверки настройки и блокировать запросы до исправления или выключения прокси. Ошибка соединения или авторизации не включает прямой доступ автоматически.

При смене прокси освобождать прежние кэши сетевых клиентов и простаивающие соединения. Уже выполняющееся видео может завершить прежние запросы; новые используют сохранённую конфигурацию.

## Альтернативы и последствия

Глобальный java.net.Authenticator затрагивает все соединения процесса; вместо него применяется авторизатор конкретного OkHttp-клиента. Собственный прокси проекта потребовал бы обслуживания и передачи через него пользовательского трафика. Пользователь указывает свой сервер; обычный HTTP-прокси не шифрует собственную Basic-авторизацию, а содержимое целевого HTTPS остаётся защищённым TLS. SOCKS5 добавляется отдельным изменением в эту же форму.
