# ADR-0131: Порционный разбор данных списков

Дата: 2026-11-10

Статус: Принято

Уточняет [ADR-0127](0127-shared-list-preparation-window.md): весь ответ сайта сохраняется, но нативные записи большого списка создаются по мере просмотра.

## Контекст

Полная выдача каталога содержит около 34 тысяч ссылок. Её разбор не заполняет кэш данных карточек, однако создаёт тысячи лёгких записей, которых пользователь обычно не достигает. В debug-сборке эмулятора полный разбор в разных прогонах занял 4–19 секунд и добавил около 9–11 МБ занятой памяти. Первые 250 записей разбирались за 76–261 мс. Удерживаемые нативные записи первой порции заняли в среднем около 82 КБ по серии из 20 образцов, без буферов открытого парсера. Эти измерения не заменяют проверку производительности на Ugoos.

## Решение

- Общий `ListParsingWindow` разбирает первую порцию до 250 записей. При выборе 200-й записи запускается следующая порция до 250; затем пороги составляют 450, 700 и далее. Одновременно выполняется одна порция, в фоновом потоке.
- Размер порции `LIST_PARSE_BATCH_SIZE = 250` и запас `LIST_PARSE_AHEAD = 50` находятся в `data/settings/CacheSettings.kt`, рядом с размером кэша данных карточек. В интерфейс эти значения не выводятся.
- Общий механизм используется разборщиками публичных и личных списков, поиска и каталога. Разборщики форматов различаются: небольшой HTML и JSON сохраняют свои средства чтения; каталог продолжает потоковый разбор из дискового HTML, сохраняя курсор и освобождая обработанные элементы дерева.
- Небольшой список исчерпывается в первой порции. Уже разобранные записи большого списка остаются в памяти и используются при возвращении. При переключении раздела курсор сохраняется; смена условий, владельца или уничтожение модели закрывают прежний курсор.
- У окна разбора и окна подготовки карточек разные задачи. Общий движок получает доступные записи и по прежним правилам готовит карточки, описания и постеры. Галочка предзагрузки управляет их подготовкой, а не размером порции разбора. Сам разбор не заполняет кэш данных карточек на 5000 сезонов.
- Число найденных записей до конца разбора показывается с плюсом: `250+`, затем `500+`; после конца — точное число. Не отправлять отдельный запрос количества только ради этой подписи.
- Серверная пагинация продолжает добавлять данные в тот же список. Следующую серверную страницу запрашивать после разбора доступной; это не второй движок отрисовки.
- Ошибка позднего участка сохраняет уже показанные записи и даёт возможность обновить источник. Не объявлять нераспознанный ответ пустым списком. Начало и конец разбора проверяются отдельно.

## Альтернативы и последствия

Полный разбор прост, но увеличивает задержку первого показа и расход памяти. Повторный разбор HTML с начала при каждом достижении порога многократно выполняет одну работу. Хранение только последних 250 разобранных записей усложняет возврат и восстановление фокуса. Выбран продолжаемый курсор с накоплением записей.

Полный HTTP-ответ по-прежнему приходит без серверной пагинации и проходит ограничение распакованного размера общего транспорта. Окно сокращает разбор и удержание нативных записей; оно не уменьшает объём скачиваемой выдачи.
