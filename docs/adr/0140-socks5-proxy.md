# ADR-0140: SOCKS5 в общей настройке прокси

Дата: 2026-11-11

Статус: Принято

## Контекст

HTTP CONNECT из ADR-0139 не покрывает серверы SOCKS5. Нужны оба протокола, каждый с авторизацией и без неё, при общей форме и одинаковой защите настроек.

## Решение

Добавить «SOCKS5» в существующий выбор типа прокси. Остальные поля, сохранение, отмена, Android Keystore и отсутствие прямого подключения при ошибке общие с HTTP CONNECT. Сохранённый тип `http_connect` сохраняет смысл; `socks5` — отдельное значение того же формата.

Использовать SOCKS5 CONNECT по RFC 1928. Без логина и пароля предлагать метод 0, с ними — только метод 2 и авторизацию RFC 1929. Не менять глобальный java.net.Authenticator. При настроенной авторизации не соглашаться на переход к методу без неё. Логин и пароль кодируются UTF-8, каждый занимает 1–255 байт; для HTTP CONNECT прежние ограничения сохраняются.

Передавать имя целевого сервера прокси, без предварительного DNS-запроса к этому имени на устройстве. IPv4 и IPv6 передавать в бинарных форматах SOCKS5. DNS приложения разрешает только имя прокси. Адаптер маршрутов возвращает IP прокси с сохранённым именем целевого сервера: OkHttp перебирает адреса прокси обычным способом, сокет соединяется с выбранным адресом и выполняет SOCKS CONNECT. Он остаётся обычным подключённым Socket, пригодным для системного TLS и DPI-обхода. Для таких маршрутов использовать HTTP/1.1: IP обозначает прокси, поэтому объединение HTTP/2-соединений разных серверов по этому IP недопустимо.

Проверять версию и метод авторизации, статус и формат ответа CONNECT, длины и конец потока. Ограничивать время рукопожатия, при отказе закрывать сокет. TLS, проверка имени конечного сервера и pins выполняются после установки туннеля общими клиентами сайта и видео.

## Альтернативы и последствия

Системная реализация SOCKS5 с паролем использует глобальный Authenticator и связывает независимые соединения процесса; отдельное рукопожатие ограничивает учетные данные конкретной конфигурацией. HTTP CONNECT остаётся самостоятельной альтернативой. SOCKS5 и RFC 1929 сами не шифруют авторизацию; HTTPS внутри туннеля сохраняет защиту содержимого. UDP и SOCKS4 в задачу не входят.
